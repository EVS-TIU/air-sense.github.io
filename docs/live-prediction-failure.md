# Live Vercel: “Prediction unavailable: Failed to fetch” — diagnosis

Date: 2026-11-19. Status: diagnosis complete, fix pending. All values below are
measured, not inferred; where something is inferred it is labelled as such.

## 1. Symptom (reproduced on the live domain)

Live page: `https://air-sense-web.vercel.app/climate-analysis/climate-analysis-2.html`.
The page pins the API with `<meta name="airsense-api-base" content="https://airsense-backend-docker.getvoroa.com/api/v1">`
and `window.ClimateApi.API_BASE` resolves to that URL (verified in the browser).

Reproduction in the live page, using the app’s own API helper:

```js
window.ClimateApi.getClimateForecast(
  { lat: 22.70, lon: 88.40, city: 'Sukant Nagar', country: 'India' },
  '2026-12-31'
)
```

Result after **66,027 ms**: `TypeError: Failed to fetch`. The same text appears
in both places the user sees: `Prediction unavailable: Failed to fetch` (the
card) and `Prediction failed: Failed to fetch` (the overview). This is a
transport/CORS-level error, not a handled HTTP status.

The Weather Chat reply in the same session contains live numbers plus “The LLM
is briefly unavailable (provider rate limit or timeout)”, so that request *did*
reach the backend: CORS and the API host are reachable for other endpoints.

## 2. Measured live behaviour

Requests to `https://airsense-backend-docker.getvoroa.com/api/v1/climate/predict`
with `Origin: https://air-sense-web.vercel.app` (all lat `22.70`, lon `88.40`,
Sukant Nagar):

| Target date | Result | Time |
|---|---|---|
| 2026-12-01 | HTTP 200 | 77.2 s |
| 2026-12-05 (repeat/cached) | HTTP 200 | 0.9 s |
| 2026-11-21 (fresh, short range) | HTTP 200 | 51.4 s |
| 2026-12-31 (windows cross New Year) | Cloudflare **502**, body `error code: 502`, no `access-control-allow-origin` | 82.8 s, 69.6 s |
| 2026-12-20 (outlook, no wrap) | HTTP 200 | 1.2 s (cache populated by an earlier in-flight request) |
| 2027-01-02 (windows cross New Year) | Cloudflare **502** | 68.3 s |

`GET /health` returns `{"status":"ok"}` in ~0.3 s immediately after a 502, so
the container is alive. The 502 is generated by Cloudflare (`server:
cloudflare`, `error code: 502`), and it carries **no CORS header** — a browser
fetch therefore reports the opaque `TypeError: Failed to fetch` instead of an
HTTP error. The mapping 502 → “Failed to fetch” is confirmed by the browser
probe and the response headers; what made the edge/origin drop the connection
at ~68–83 s is **inferred** (long request closed by the gateway / origin),
because server logs are not available from here.

## 3. Confirmed code defect: year-wrapping history window

`backend/app/climate_predict.py`, `_history_year()`:

```python
start = date_type(year, window_start.month, window_start.day)
end   = date_type(year, window_end.month, window_end.day)
```

`window_start = target - HISTORY_WINDOW_DAYS`, `window_end = target +
HISTORY_WINDOW_DAYS` (`HISTORY_WINDOW_DAYS = 2`). For a target of 31 Dec, that
window is 29 Dec – 2 Jan. Substituting the month/day into *one* year produces
`start=YYYY-12-29`, `end=YYYY-01-02`, i.e. `start > end`. Open-Meteo answers
**400 Bad Request**, and the historical-forecast fallback answers 400 too.

Local reproduction with target 2026-12-31 (fresh coordinates) produced ten
pairs of failed calls:

```
Historical fetch 2025-12-29..2025-01-02 failed: Client error '400 Bad Request'
Historical fetch 2024-12-29..2024-01-02 failed: 400
... (2023, 2022, 2021)
ClimatePredictError: No historical archive data available for this location
```

Each failed year goes through archive attempts (`attempts=2`) and then the
fallback host (`attempts=3`) with backoff. Ten years of that burns tens of
seconds before failing — matching the live ~68–83 s stalls for 31 Dec and
2 Jan, and explaining why normal dates (e.g. 20 Dec, 21 Nov) work.

## 4. Contributing latency problem

A normal-date local run (target 2026-11-25) made **10 HTTP calls / 10.3 s**, of
which **6 were sequential archive requests**:

```
archive 2025-11-23..2025-11-27
archive 2024-11-23..2024-11-27
archive 2023-11-23..2023-11-27
archive 2022-11-23..2022-11-27
archive 2021-11-23..2021-11-27
archive 2016-11-25..2026-11-19   (the MLP's 10-year contiguous fetch)
```

The 5 per-year calls fetch 5-day windows that are already contained in the
10-year contiguous response fetched later for the MLP. On the live 0.1 vCPU
target this duplication costs ~50 s for a fresh prediction (measured), leaving
no headroom before the gateway’s ~60–100 s limit.

Two more latency risks:
- `ClimatePredictService.client` uses `httpx.Timeout(60.0, connect=10.0)` and
  `_agent_adjust()` awaits the LLM before returning. Weather Chat reports the
  LLM is currently failing; a 60 s wait there alone can kill a prediction.
  (Chat itself uses a 20 s timeout.)
- The failure is surfaced as raw “Failed to fetch” because a CORS-less gateway
  page cannot be read by the browser.

## 5. Fix plan

1. Build each year’s window from a real centre date (`date(year, target.month,
   target.day) ± HISTORY_WINDOW_DAYS`), so 29 Dec–2 Jan becomes a valid range
   across the year boundary; handle 29 Feb.
2. Fetch the archive once (the contiguous 10-year range already needed by the
   MLP), derive both the 5-year climatology and the MLP samples from those
   rows, and cache those rows per location. Fall back to the old per-year path
   if that single fetch fails. This removes 5+ sequential round trips.
3. Cap the climate LLM agent call at ~10 s (connect ~5 s) so a failing provider
   cannot stall the whole prediction.
4. Translate `TypeError: Failed to fetch` into a clear “prediction timed out /
   server too slow, retry” message in the frontend.
5. Add regression tests for the year wrap and the shared archive fetch.

## 6. Verification plan (after the fix)

- Unit/integration: full test suite; a fresh 2026-12-31 / 2027-01-02 prediction
  must return data (no 400s), with a valid temperature and climatology.
- Instrumented local call count: archive requests per fresh prediction must
  be 1 (plus fallback only on failure), down from 6.
- Slow-LLM simulation: point the agent at a hanging endpoint and confirm the
  prediction returns within the new cap.
- Second date for the same location must be served from the archive cache.
- Live verification requires redeploying the backend behind
  `airsense-backend-docker.getvoroa.com`; only after that can the live 502 for
  year-boundary dates be declared fixed. No live claim before measuring.

## 7. Server-side confirmation from deployed logs (2026-11-19)

The user supplied the live container’s log tail. It confirms the diagnosis
directly, rather than by inference:

- For `date=2026-12-31` (both the user’s coordinates `22.5583,88.4143` and
  `22.7000,88.4000`), the server logged inverted windows for every year:
  `2025-12-29..2025-01-02`, `2024-12-29..2024-01-02`, … `2021-12-29..2021-01-02`.
  Each one got `400 Bad Request` from `archive-api.open-meteo.com`, then the
  `historical-forecast-api.open-meteo.com` fallback also returned `400`. The
  request ended with `502 Bad Gateway`. This is exactly the start-after-end
  window produced by `_history_year()`.
- For `date=2027-01-02`, the same pattern appears with windows
  `2025-12-31..2025-01-04` … `2021-12-31..2021-01-04`, ending in another
  `502 Bad Gateway`.
- A Uvicorn restart (`Started server process [6]` … `Application startup
  complete.`) is visible, but the post-restart requests still log the inverted
  ranges — so the deployed image still contains the old code. The local fix is
  not live yet.
- Non-boundary dates (`2026-12-01`, `2026-12-05`, `2026-11-21`, `2026-12-20`)
  returned `200 OK`, and the log line `LLM climate agent unavailable; using
  deterministic blend` shows the LLM fallback path completing normally. This
  rules out the LLM as the cause of the 502.
- Separate issue, not the cause of this failure: `app.ai_chat` repeatedly logs
  `401 Unauthorized` for `https://openrouter.ai/api/v1/chat/completions`,
  i.e. the configured LLM key is invalid/expired. That explains the chat
  fallback notice, but predictions still succeed for normal dates with the
  deterministic blend.

Expected log signature after the fixed backend is deployed: one
`archive-api.open-meteo.com` call for `2016-01-01..<today>` per location (no
inverted ranges), followed by `climate/predict ... 200 OK` for
`date=2026-12-31` in roughly 10 s.

## 8. Follow-up (2026-11-20): latency, not correctness

Measured again after the range/year-wrap fixes reached the live image:

| Live request | HTTP | Time |
|---|---|---|
| `/health` | 200 | 0.19 s |
| `climate/predict` d+1 | 200 | 52.7 s |
| `climate/predict` d+15 | 200 | 57.0 s |
| `climate/predict` d+88 | 200 | 63.9 s |
| `climate/predict` d+365 | 200 | 52.6 s |
| `climate/predict` d+366 | 400 + exact range message | 0.98 s |
| `climate/predict` 2026-12-31 / 2027-01-02 (year wrap) | 200 | 74.4 / 59.6 s |

So the deployed code is current — out-of-range and year-boundary dates now
behave correctly. The remaining failure is **pure latency**: a cold live
prediction takes 52–74 s, while the browser fetch (and the CDN gateway around
60–66 s) gives up first and surfaces the opaque “Failed to fetch” → the two
error strings in the report. A repeat of any of those dates is served from the
server cache in <1 s.

The live `aiInsight` is the deterministic fallback, matching an LLM that is
still unavailable/oversized in the deployed environment; that only costs a few
seconds thanks to the 5 s cap, so it is not the dominant term on a 0.1 vCPU box.

### Fixes applied in this round

1. **Frontend (auto-deployed by Vercel):** `getClimateForecast()` now bounds each
   attempt at 50 s and retries up to 3 times. Because the backend caches every
   *completed* prediction, a retry after a gateway-dropped request is normally
   served from cache and resolves in under a second. 4xx responses (including
   the exact out-of-range message) are never retried. The loading text now sets
   the expectation that the first run for a date can take about a minute.
2. **Backend (needs a Voroa redeploy):** `_open_meteo()` no longer retries
   permanent 4xx responses — it previously retried HTTP 400 three times with
   backoff, which is exactly what hourly AQI does for any date past the
   provider's ~6-day horizon. `_hourly_aqi()` now skips those calls entirely;
   `predict()` already holds the current daily AQI flat across the 24 h axis in
   that case. Measured locally: cold prediction 15.3 s → 6.0 s, HTTP calls
   3 → 2 for a far-future date.

Verified locally: `node --check` on the frontend file, backend `py_compile`,
and `68 passed` (one pre-existing unrelated `test_missing_api_key` failure).

### Live verification (2026-11-20, headless Chrome on the Vercel page)

After `34f9bc6` was deployed by Vercel:

- Fresh in-range date `2027-09-14` for Sukant Nagar: the real page event
  (`weatherly:prediction-date`) rendered the full prediction in **56 s**, one
  fetch attempt, no error. Dashboard showed condition, temperature, AQI and the
  trained-model note; the overview showed the explanation text.
- A repeat date was served from cache instantly.
- Out-of-range date `2028-01-01`: **0** prediction API calls and the exact
  message `You have selected out of the predict range. Choose a date from
  today up to 1 year ahead.` in both the status and the overview.

A 50 s single-attempt timeout with three retries was tried first and rejected:
each client abort leaves the server computing, so retries pile extra work onto
the 0.1 vCPU container and can exhaust the whole budget. The deployed setting
is a 180 s single-attempt budget plus one retry (needed only when the CDN drops
the connection, in which case the completed result is already cached).

Live verification of the **backend** half (4xx no-retry, skipped hourly AQI)
still requires a fresh Voroa deploy; no deploy webhook is exposed on the repo.
